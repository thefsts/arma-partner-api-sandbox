# ARMA Partner API Sandbox

Temporary sanitized public integration workspace for ARMA System 360 partner APIs.

## Purpose

This repository contains only the integration-facing code, contracts, synthetic tests, and documentation needed to continue development without exposing the private repositories or their Git history.

Current lanes:

- `law-shield/` — ARMA System 360 <-> Law Shield secure transfer API. Law Shield remains a legally and technically separate system.
- `patches/` — ARMA System 360 <-> PATCHES partner API. PATCHES remains an independent licensed platform and is Phase 2 for ARMA launch.

## Non-negotiable boundaries

- No production secrets, tokens, credentials, private keys, customer data, incident evidence, privileged Law Shield data, LISA/legal packages, or private Git history.
- ARMA must not directly query Law Shield or PATCHES databases.
- Law Shield and PATCHES must not directly query ARMA databases.
- All examples and tests must use synthetic data.
- Integration must fail closed when authentication, authorization, mapping, integrity, processor, or receipt verification fails.
- Do not rebuild the obsolete embedded ARMA Attorney Portal.

## PATCHES partner API (Stop Point 4)

PATCHES remains an independent licensed privacy/protection platform; ARMA System 360 integrates through this scoped partner API only — no direct database access, no PATCHES private protection algorithms in this sandbox. `patches/lib/server.ts` implements the complete sanitized reference `PATCHES Partner API v1` built up from the original health endpoint, exercised over real HTTP in `patches/tests/partner.api.test.mjs`:

- **Routes** (all under `/api/partner/v1`): `GET /health` (live, never force-static cached), `GET /capabilities`, `GET /entitlements?orgId=`, `POST /activations` (idempotent), `GET /activations/:id`, `POST /activations/:id/deactivate`, `POST /activations/:id/revoke`, `GET /events?orgId=`, `GET /audit?orgId=`
- **Authentication** — `Authorization: PATCHES-Partner <clientId>:<keyId>` with HMAC-SHA256 request signing over method/path/timestamp/nonce/bodyHash, timing-safe comparison, ±5 min clock skew, nonce replay registry, credential lifecycle (rotation with grace, revocation, suspension)
- **Authorization chain** — partner → organization → entitlement → capability → binding; the authenticated partner principal is the only source of truth, `orgId`/`deviceId`/`subjectId` from the request body are never trusted directly
- **Tenant isolation** — organizations carry an `owningPartnerId` boundary; wrong-tenant reads AND writes fail closed
- **Activation lifecycle** — idempotency key + request hash (duplicate collapse vs. 409 conflict), opaque synthetic device/subject bindings (no PII), revocation is terminal
- **Receipts/audit** — the response body is the signed receipt (HMAC over raw response bytes; `X-PATCHES-Receipt-Id`, `X-PATCHES-Content-SHA256`, `X-PATCHES-Signature`); append-only, sanitized, tenant-scoped audit trail
- **Operational controls** — request IDs / correlation IDs, structured error codes, payload limit (413), per-clientId reference token-bucket rate limiting (429 + `retry-after`, checked after auth so anonymous floods cannot starve partners), fail-closed downstream boundary (injectable protection service; failure → 503 with zero partial state), and a kill switch (`PATCHES_PARTNER_API_DISABLED`) that fails every route closed while health reports the disabled state live
- **Test matrix** — the 27 mandatory contract scenarios (auth, tenant isolation, entitlements/capabilities, activation/idempotency, replay/tamper, receipts/audit, rate limit, downstream failure, kill switch) plus sub-scenarios, all driven against a real ephemeral-port HTTP server with contract-signed requests and an injectable clock
- Generic contract identifiers only (`traffic_stop_privacy`, `home_privacy`); synthetic data only

Remaining production-only PATCHES work (private repo): Convex persistence port, push/event delivery infrastructure, production key/secret rotation, production rate limiting, production tenancy checks, quarantine tooling. See `patches/docs/API-BUILD-SCOPE.md` and `docs/STOP-POINT-4-REPORT.md`.

## ARMA PATCHES adapter (Stop Point 5)

`patches/arma/` implements the ARMA-side integration half of the PATCHES partner contract — the client library, durable activation state machine, and reference persistence the future Alert ARMA / Domus systems will consume. It contains **no** Alert ARMA UI, **no** Domus UI, no proprietary PATCHES logic, and no direct database access: the only boundary is the authenticated partner API itself.

- **`patches/arma/patchesPartnerClient.ts`** — scoped partner auth (`PATCHES-Partner <clientId>:<keyId>` + HMAC-SHA256 canonical signing over method/path/timestamp/nonce/bodyHash with fresh nonce per attempt), bounded retry with backoff + `retry-after` honoring, and the failure classification engine implementing the owner's binding amendment: **CLEAN_RETRYABLE** (pre-delivery connection failures, authenticated 429, provably-unprocessed 503/500) get a bounded retry with a fresh nonce+signature; **AMBIGUOUS** (timeout after possible delivery, response/receipt lost, receipt integrity mismatch) **never blind re-send** — they transition the activation to `RECONCILIATION_REQUIRED`; **TERMINAL** (credential/tenant/entitlement/capability/binding denials, state conflicts) are rejected or quarantined. Receipts are verified over the exact raw response bytes; signatures are never recorded in attempt evidence (secret-free audit by construction).
- **`patches/arma/activationService.ts`** — durable state machine `PENDING → READY_TO_ACTIVATE → ACTIVATION_SENT → RECEIPT_VERIFIED → ACTIVE` plus `RECONCILIATION_REQUIRED`, `DEACTIVATED`, `REVOKED`, `REJECTED`, `QUARANTINED`. Stable idempotency key per ARMA activation intent; `ACTIVATION_SENT` persisted **before** the outbound await (crash mid-send ⇒ resume reconciles, never re-sends); entitlement/capability preflight fail-closed before any outbound call; in-flight intents own their binding (a different caller key collapses via `INTENT_KEY_MISMATCH`, never a parallel server-side activation); reconciliation via the status route with bounded attempts then a fresh create under the **same** idempotency key; tenant-scoped status resolution (a foreign-org identity is quarantined, never synced); an outbound kill switch (`ARMA_PATCHES_OUTBOUND_DISABLED`) that fails closed before any wire I/O; human/system audit events (secret-free) at every transition.
- **`patches/arma/transferSchema.ts` + `patches/arma/armaStore.ts`** — 11-table Convex-shaped reference persistence (partner config, org mappings, entitlement/capability refs, opaque bindings, activations, idempotency, receipts, retries, reconciliations, audit chain) with no PII, backed by an in-memory store with transactional snapshot/restore semantics for the port to Convex.
- **`patches/tests/partner.client.test.mjs`** — 48-test matrix: classification engine units, live signed activation through the real SP4 reference server, auth failures (unknown partner, revoked/rotating credentials with grace windows, expiry), tenant/entitlement/capability/binding rejections, idempotency duplicate/conflict/collapse, 429 bounded retry, clean 503/500 retry, ambiguous-failure reconciliation (timeout / response lost / receipt signature / field mismatch), lifecycle (deactivate/revoke, terminal revoked never silently reactivated, replay, stale timestamp), both kill switches, wrong-org reconciliation denial, and a full synthetic E2E — with `assertNoSecretsInStore` defense-in-depth throughout.

Remaining production-only adapter work (private repo): Convex function port of the 11 tables, real KMS-backed secret sources, production reconciliation scheduling, quarantine operator tooling, Alert ARMA / Domus UI wiring (deliberately out of scope). See `docs/STOP-POINT-5-REPORT.md`.

## AI Safety + Governance contract (Stop Point 6)

`ai-governance/` implements the reusable integration-facing AI governance layer — the five designations, engine registry, provenance envelopes, guards, protected-action policy, and audit. It contains **no** private ARMA AI engine implementations and **no** prompts or model keys: proprietary engines (MILAN, JOY, ROSE, RERE, DALINN and others) remain private; here they only ever appear behind registered synthetic engine identities on their one legal lane. Everything fails closed: unknown engines, unknown actions, unknown actor classes, stale policy versions, and tampered envelopes are denials and audit events, never silent passes.

- **Five designations / four engine classes** — `AI_ADVISORY`, `DETERMINISTIC_RULE`, `HUMAN_AUTHORIZATION`, `SYSTEM_AUTOMATION` (four engine classes; AI engines register advisory-only by structural rule) and `EXTERNAL_PARTNER_DATA`. Generative AI may only register on the advisory lane; rule engines register separately from generative AI, exactly as the owner's directive requires.
- **Seven AI_MAY task types** — `analyze`, `summarize`, `classify`, `recommend`, `identify_issues`, `flag_for_review`, plus advisory-only structural lanes; every other task type fails closed on registration and on every guarded call.
- **15 AI prohibitions** — guard-enforced in both directions: AI output may never carry authorization, admin/role/credential claims, tenant/entitlement overrides, audit or review suppression, evidence destruction, retention bypass, human impersonation, or smuggled instructions to other systems; partner data may never carry prompt-injection, tool/function calls, privilege escalation, RBAC changes, policy bypass, secret extraction, or fake system/developer messages.
- **Protected-action registry (exactly 10)** — `LAW_SHIELD_DISCLOSURE`, `EVIDENCE_DESTRUCTION`, `AUDIT_MUTATION`, `RBAC_CHANGE`, `ADMIN_GRANT`, `PARTNER_CREDENTIAL_CHANGE`, `TENANT_OWNERSHIP_CHANGE`, `ENTITLEMENT_OVERRIDE`, `SECURITY_POLICY_OVERRIDE`, `RETENTION_HOLD_CHANGE`. AI is never an allowed actor on any of them; unknown actions fail closed (`DENIED`); rule engines may only automate the fail-closed direction (e.g. auto-blocking an evidence destruction under a retention hold) — never an approval; human authorization requires an authenticated, authorized, org-scoped reviewer of record bound to the exact governed output hash.
- **Provenance envelopes** — every advisory output can be bound to engine ID + version, task type, designation, timestamp, source references, confidence, `humanReviewRequired`/`reviewingHumanId`/review timestamp, output hash (SHA-256), policy version, and audit ID, sealed with an HMAC integrity tag over the fixed-order bound values. Verification recomputes the tag (metadata tamper → `METADATA_TAMPERED`), the output hash (byte tamper → `OUTPUT_TAMPERED`), engine registration, designation, classification, freshness (±5 min skew), and policy version — in that order, all fail-closed. An equivalent deterministic-result envelope exists for rule-engine outputs.
- **Append-only, metadata-only audit** — audit records carry identifiers, reason codes, hashes, and counts; record-time rules throw on prompt/key/secret-material keys and content keys, and secret-value containment is detected and audited; mutation attempts are refused and the refusal itself is audited.
- **Test matrix** — `ai-governance/tests/` (56 tests): vocabulary/registration fail-closed, every guard sample table empirically verified against the real guards before assertion (33 injection samples + 31 AI-authority samples, one per pattern id, each rejected with its pattern id and reason code, audited without content), embedded instruction keys, depth/size structural limits, clean-data verbatim classification with content hashes, human review eligibility/binding/durability, the full 10-action protected-action matrix (AI denied on all ten, deterministic fail-closed-only, human authorization paths), provenance create/verify across tamper/stale/unknown/cross-store cases, and an end-to-end chain: partner data → guard → advisory output → provenance → AI denied → human review → durable approval, plus an injection short-circuit variant, a post-approval tamper variant caught at every checkpoint, and cross-org isolation.
- Synthetic sandbox material only (synthetic integrity key, synthetic policy version); production keys and engine wiring live in the private repos. See `docs/STOP-POINT-6-REPORT.md`.

## Shared partner integration platform (Stop Point 7)

`shared/` implements the integration-facing contracts every partner surface shares — the partner SDK primitives, the partner/entitlement/capability registry, the signed webhook/event framework, and the integration observability contract — extracted from the proven Law Shield + PATCHES seams so no partner lane ever re-implements signing, receipts, retries, or fail-closed authorization. It contains **no** private ARMA, Law Shield, or PATCHES implementation, **no** credentials or prompts, and **no** production data: every secret in it is a synthetic sandbox value, and every surfaced surface is metadata-only (identifiers, reason codes, and hashes — never payload content).

- **Shared SDK (`shared/sdk/`)** — canonical 5-field request signing (`METHOD\npath\ntimestamp\nnonce\nbodyHash`, HMAC-SHA256 hex, timing-safe comparison, ±5 min clock skew, body-hash binding over the exact raw bytes); platform receipts (HMAC over raw response bytes with `expected`-field binding, so a receipt can never prove a different operation); idempotency (FRESH / DUPLICATE collapse vs. request-hash-mismatch CONFLICT) plus a nonce replay guard with a bounded validity window and pruning; request/correlation IDs (echo-valid-or-generate, child derivation with a depth bound, propagation headers); exact-match API version negotiation with per-capability min/max windows; structured errors (one error-code vocabulary, coarse error classes, a partner-visible safe-context allowlist, and the `toResponse()` body shape); the clean-retryable-only retry policy (schedule `[1s, 5s, 30s, 2m, 10m]`, CircuitBreaker CLOSED → OPEN → HALF_OPEN canary) where AMBIGUOUS outcomes route to reconciliation and are never blindly re-sent; health/readiness (REQUIRED vs. OPTIONAL dependencies → AVAILABLE / DEGRADED / UNAVAILABLE); and the `PartnerSdkClient` façade composing it all (buildRequest / processResponse / planRetry / verifySignature). A 2xx without a verifiable receipt FAILS CLOSED — a success is only trusted when its receipt proves it.
- **Partner registry (`shared/registry/partnerRegistry.ts`)** — the authorization chain org → binding → entitlement → capability → status → API version window, resolved as data (no hardcoded partner logic anywhere); every unknown or inactive element fails closed with a typed code (`PARTNER_UNKNOWN`, `ORG_NOT_BOUND_TO_PARTNER`, `BINDING_INACTIVE`, `ENTITLEMENT_EXPIRED`, `CAPABILITY_VERSION_UNSUPPORTED`, ...).
- **Secure webhook/event framework (`shared/webhooks/`)** — a closed event-type vocabulary; metadata-only envelopes (allowlisted data keys, scalar values, bounded strings); canonical signing with a fresh nonce per delivery attempt; receiver-side verification over raw bytes (header presence → schema/timestamp skew → nonce replay → body hash → HMAC → envelope validation → event-ID replay → per-stream strict sequence ordering, all fail-closed) behind `WebhookEventGuard`; and `WebhookDeliveryService` with duplicate collapse (a delivered event is never re-sent), the proven retry schedule, and immediate dead-lettering of ambiguous outcomes.
- **Observability contract (`shared/observability/telemetry.ts`)** — telemetry spans (request ID, partner, operation, status, latency, retry count, reconciliation status) with a metadata-only allowlist: forbidden material/content keys throw structurally, and registered secret values can never appear in any span.
- **Audit integration (`shared/sdk/audit.ts`)** — `IntegrationAuditTrail` wrapping the SP6 append-only `AuditLog`: metadata-only details, provenance references by ID + output hash, mutation refused and the refusal itself audited.
- **Test matrix** — `shared/tests/` (207 tests): every SDK primitive unit-tested (signing 18, receipts 11, idempotency 14, correlation 18, errors 15, retries 14, health 12, audit 13, client 18), the full registry authorization matrix with every typed failure code (17), webhook build/sign/verify/guard/delivery including dead-letter and duplicate collapse (28), the telemetry span lifecycle with secret-containment assertions (18), and a full synthetic end-to-end chain (11): registry resolve → version negotiate → signed request → server-side verify → replay burn → idempotency → signed receipt → receipt verification → webhook event → retrying delivery → receiver verification → telemetry span → audit — with fail-closed unknowns (partner, capability, forged receipt, tampered signature, unknown event type) and no-payload-leak assertions on every surfaced surface.

Synthetic sandbox material only (synthetic signing/receipt/webhook secrets, synthetic partner/org/entitlement records); production keys, real partner records, and durable persistence live in the private repos — each in-memory registry is shaped for a unique-index port (see the PORTING NOTEs in the modules). See `docs/STOP-POINT-7-REPORT.md`.

Alert ARMA / Domus UIs remain Stop Point 8+ (proposal only — not begun).

## Synthetic partner simulators + failure-mode harness (Stop Point 8)

`simulators/` builds the contract test harness that proves every shared integration surface against synthetic partners before any real one is connected — in-process partner simulators built ON the shared SDK, a configuration-driven failure-mode harness, and one contract runner driving every simulator × failure-mode combination. It contains **no** real partner logic, **no** credentials, and **no** network: every secret is a synthetic sandbox value, every clock is injected, every exchange happens in-process, and all surfaced evidence is metadata-only (identifiers, reason codes, and counts — never payload content, never envelope bodies).

- **Simulator behaviors (`simulators/behaviors.ts`)** — the data layer: three synthetic simulator identities (well-behaved, alternate-entitlement, alternate-capability) resolved through the SP7 registry as pure data (partner/org/binding/entitlement/capability records — registry data, not code); synthetic sandbox secrets (`synthetic-sim-*-SP8-sandbox`); an injected scenario clock; the `ScenarioConfig` fault plan vocabulary (authorization flips, partner/platform fault plans, receipt faults, downstream behavior, circuit plan, transport script steps, receiver faults, delivery plan, kill switch); and `wellBehavedScenario(identity)` — the pure happy-path seed every failure mode is derived from.
- **Partner simulator (`simulators/partnerSimulator.ts`)** — a simulated partner client built on the shared SDK: signs requests with the canonical 5-field scheme, verifies platform receipts over raw bytes, collapses duplicates through SDK idempotency, computes retry plans per attempt index, records transport calls, and fails closed on every untrusted response. Configuration-driven only — the same engine runs every identity and every fault plan with zero partner-specific branching.
- **Synthetic platform (`simulators/syntheticPlatform.ts`)** — the in-process partner platform: registry-resolved authorization (fail-closed typed codes), signature/timestamp/nonce/replay verification, receipt issuance and faulted receipts (omitted/forged/tampered/wrong-operation), idempotency and conflict presentation, transport scripting (ok/clean-retryable/ambiguous/timeout), downstream availability gating, circuit-breaker state transitions, webhook event emission and ordered delivery with receiver faults (re-presented deliveries, tampered bodies, ordering gaps), dead-lettering, reconciliation, and kill switches — every phase driven by the scenario's fault plan, observed through metadata-only views.
- **Failure modes (`simulators/failureModes.ts`)** — the deterministic harness: 40 failure modes across 10 categories (SIGNATURE, REPLAY, RECEIPT, AUTHORIZATION, ENTITLEMENT, WEBHOOK, RETRY, RECONCILIATION, CIRCUIT_BREAKER, KILL_SWITCH), each declared as a pure injector `wellBehavedScenario(identity) → faulted ScenarioConfig` with its expected contract code and evidence surface. Modes are data transformations — the engines apply them mechanically; attack-presentation modes (replay, tamper, forged receipts) must be refused the attack presentation itself, while fail-closed modes never produce a trusted success on their declared surface.
- **Contract runner (`simulators/contractRunner.ts`)** — one runner driving every simulator × failure-mode combination (3 simulators × 40 modes + 3 control scenarios = 123 scenarios, all PASS) against the shared contracts, with contract checks per scenario (expected code observed, fail-closed discipline held, retry plan correct, receipt reason surfaced, delivery/dead-letter/attempt counts, circuit states, event emission, span status, reconciliation status) and defense-in-depth: a broken or throwing failure mode fails closed as a typed FAIL row — never a crash, never a silent skip.
- **Evidence (`simulators/evidence.ts`)** — metadata-only scenario evidence (20 allowlisted keys, frozen records, bounded strings/lists, no payload content) plus `certificationRowFor` mapping to the Stop Point 10 certification reporting shape `{testId, category, requirement, result, reasonCode}` — PASS rows carry the expected code, FAIL rows carry the observed code.
- **Test lane** — `simulators/tests/` (53 tests): the full happy-path chain through the shared SDK (7), configuration-driven behavior across all three identities (24), the failure-mode catalog with the fail-closed discipline sweep (10), and the contract runner matrix with certification rows, tallies, determinism, and fail-closed runner paths (12).

Synthetic sandbox material only (synthetic simulator secrets, synthetic registry records, injected clocks); no real network, no real partner, no production data. See `docs/STOP-POINT-8-REPORT.md`.

## OpenAPI contracts (Stop Point 9)

`openapi/` and `law-shield/openapi/` contain the machine-readable **OpenAPI 3.1** contracts for both partner-facing surfaces, written from the reference implementations and tests as the authoritative source (invented nothing, omitted no public surface, excluded every internal-only route and private detail), plus an in-repo test lane that keeps the documents in lockstep with the code.

- **PATCHES Partner API v1 (`openapi/patches-partner-v1.yaml`)** — the complete implemented v1 surface (9 operations under `/api/partner/v1`): the `PatchesSignedRequest` HMAC-SHA256 security scheme with its five signing headers; every route, query/parameter, request body, response schema, and error shape; the full error-code vocabulary; the version policy (only `v1`; any other version segment fails closed with 400 `UNSUPPORTED_API_VERSION`); idempotency (single-use nonces registered in the same transaction as the outcome, activation idempotency-key semantics and conflict presentation); the cumulative security model (signature verification is only the first gate — org ownership, entitlement windows, capability registration, device/subject binding, tenant scoping, and rate limiting after auth are all enforced and documented); receipt and receipt-header schemas; and the kill-switch / downstream-unavailable / persistence-failure fail-closed responses.
- **ARMA Law Shield API v1 (`law-shield/openapi/arma-lawshield-v1.yaml`)** — the complete implemented v1 surface (4 operations): the inbound gateway `POST /api/lawshield/arma` (ArmaSignedTransfer scheme with the five `x-arma-*` headers, verification order, replay guard, processor forwarding, the 15-field signed receipt with its four `X-LawShield-*` receipt headers, and every gateway error shape including the processor-mismatch 502s with `reconciliationRequired`), the unauthenticated `GET /api/lawshield/integration-readiness` readiness probe, and the service-to-service durable-processor routes `POST /process` / `GET /status` (Bearer auth, the accepted wire shape, the rejected wire shape including business rejections that return HTTP 200 with `accepted: false`, idempotency semantics, and the status/reconciliation response with audit metadata). Internal-only details (store layout, private environment variables, internal helpers) are documented out — the spec covers exactly the partner-visible wire.
- **Contract-test lane (`openapi/tests/`)** — 8 tests in three layers that keep both documents honest in CI: (1) *structure* — both specs are valid OpenAPI 3.1 documents with resolvable `$ref`s, fully described operations, and response examples; (2) *cross-check* — every implemented route is documented and every documented route is implemented, every wire error code emitted by the reference implementations appears in the spec, and every spec error token traces back to source; (3) *live conformance* — the specs are validated against the live reference servers booted in-process in CI: the real PATCHES partner-API server driven through every documented operation (health, discovery, tenant-scoped lookups, idempotent activation lifecycle, receipts, events, audit, the 400/403/409/413 error families, the version policy), and the real Law Shield gateway + durable processor + readiness servers driven end-to-end (signed transfer → receipt with signature headers, replay rejection, tamper rejection, missing-header and invalid-signature failures, readiness probe, direct processor process/status).

The generated pages are committed so partners can read the contract without running anything, and the renderer regenerates them from the YAML source whenever the specs change.

All synthetic; no network, no real partner, no production data, no external rendering service. See `docs/STOP-POINT-9-REPORT.md`.

## Promotion back to private repos

Work here is not production merely because it passes sandbox tests. Approved changes must be reviewed, secret-scanned, and then manually ported into the canonical private repositories with production configuration and CI.
