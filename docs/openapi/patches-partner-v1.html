Description

Wire contract for the PATCHES Partner API v1 (receipt protocol schema

`patches-partner-v1`).

Scope — exactly the implemented v1 surface (all routes under

`/api/partner/v1`):

* `GET /health` — live readiness (unauthenticated)

* `GET /capabilities` — capability discovery

* `GET /entitlements?orgId=...` — tenant-scoped entitlement lookup

* `POST /activations` — idempotent activation create

* `GET /activations/{activationId}` — activation status

* `POST /activations/{activationId}/deactivate` — deactivate (idempotent by status)

* `POST /activations/{activationId}/revoke` — revoke (terminal)

* `GET /events?orgId=...` — activation events

* `GET /audit?orgId=...` — scrubbed audit trail (own orgs only)

Versioning: only `v1` is supported. A request to any other version segment

(e.g. `/api/partner/v2/...`) fails closed with 400

`{ error: 'UNSUPPORTED_API_VERSION', errorClass: 'VERSION', supported: ['v1'], requestId }`.

Authentication (cumulative — never a substitute for tenant scoping):

HMAC-SHA256 request signing per the `PatchesSignedRequest` scheme. Signature

verification is the first gate only; every operation additionally enforces

organization ownership, entitlement license windows, capability

registration, and device/subject binding. Rate limiting (token bucket,

capacity 30, refill 10 per second, per clientId) applies AFTER

authentication so anonymous floods cannot consume partner quota.

Request integrity:

* timestamps must be within 300000 ms (±5 minutes) of server time

* nonces match `[A-Za-z0-9_-]{20,128}`, are single-use, and have a

600000 ms (10 minutes) validity window; a fully processed request

registers its nonce in the SAME transaction as the operation outcome

* request bodies are limited to 262144 bytes (256 KiB); every POST route

requires a JSON object body (deactivate/revoke bodies are

present-but-ignored — the activation is identified by the path)

Error shapes — two families (all JSON, all structured, no raw messages):

* handler-level errors (authentication, rate limit, malformed or

oversized body, unsupported version, unmatched route) carry `requestId`

in the body

* business-pipeline errors on POST routes (policy denials, idempotency

conflict, state conflict, unknown activation, downstream, persistence)

carry `{ error, errorClass }` WITHOUT `requestId` in the body — the

`x-request-id` response header always carries it

* `ACTIVATION_INPUT_MISSING` uniquely carries `{ error, fields }`

(no `errorClass`)

* the kill-switch 503 `PARTNER_API_DISABLED` is a single-key body

There is no 405 in this API: a method that does not match the route falls

through to 404 `NOT_FOUND` (with `requestId`).

Idempotency (`POST /activations`, keyed by clientId + idempotencyKey):

* same request hash → 200 duplicate receipt (`duplicate: true`, receiptId

`RCP-DUP-<requestId>`) that echoes the ORIGINAL activation

* different request hash → 409 `IDEMPOTENCY_KEY_CONFLICT`

* the request hash is sha256 over the serialized request object, so any

semantic difference — including extra fields — is a conflict, never a

silent duplicate

* deactivate/revoke are idempotent by STATUS (second call is a no-op

success receipt); REVOKED is terminal — deactivating a REVOKED

activation is 409 `ACTIVATION_REVOKED`

Receipts: every 200 on a POST route is a receipt signed over its EXACT raw

response bytes — verify the bytes you received, never a re-serialization:

* `x-patches-receipt-id`, `x-patches-content-sha256` (sha256 of the raw

response bytes), `x-patches-signature` (hex HMAC-SHA256 over the raw

bytes with the receipt secret)

* verification fails closed with reasons `RECEIPT_MISSING_HEADERS`,

`RECEIPT_INVALID_SIGNATURE`, `RECEIPT_CONTENT_HASH_MISMATCH`,

`RECEIPT_BODY_MALFORMED`, `RECEIPT_FIELD_MISMATCH`

* GET routes never produce receipt headers; error bodies are never

receipts

Every response carries `x-request-id` (echoing the caller's `x-request-id`

header when present, else `req-<uuid>`), `x-api-version: v1`, and

`cache-control: no-store` — except the kill-switch 503s, which are emitted

before request-id assignment and carry only the baseline headers.

Fail-closed guarantees:

* downstream protection failure (503 `DOWNSTREAM_UNAVAILABLE`) persists

NOTHING — no partial activation, no receipt, no event

* persistence failure (500 `PARTNER_PERSISTENCE_FAILED`) leaves no

partial state (single transaction) and does NOT register the nonce

* kill switch (`PATCHES_PARTNER_API_DISABLED=true`) blocks every route

except health, which reports the disabled state live (503, never

cached)

POST/api/partner/v1/activations
PatchesSignedRequest
createActivation — Create an activation (idempotent). Activations

Activation create. Pipeline (in enforcement order — all cumulative,

none replaces another): organization authorization → entitlement

(status + license window) → capability (registered + version window) →

device/subject binding (exists, ACTIVE, same org, same capability) →

idempotency resolution → downstream protection check (fail-closed) →

ONE transaction (activation + receipt + idempotency record + event +

audit).

Idempotency (clientId + idempotencyKey):

* FRESH → 200 receipt (`RCP-ACT-<requestId>`; activation

`ACT-<requestId>`; event `activation.created`)

* DUPLICATE (same request hash) → 200 duplicate receipt

(`RCP-DUP-<requestId>`, `duplicate: true`) echoing the ORIGINAL

activation — no second activation is created

* CONFLICT (different request hash) → 409 `IDEMPOTENCY_KEY_CONFLICT`

with `existingActivationId`

The request hash is sha256 over the serialized request object, so extra

body fields participate in idempotency identity.

Error-body note: business-pipeline errors (403 policy, 409 idempotency

conflict, 500 persistence, 503 downstream) carry `{ error, errorClass }`

WITHOUT `requestId` in the body — the `x-request-id` header carries it.

Handler-level errors (auth, rate limit, malformed/oversized body) DO

carry `requestId`. `ACTIVATION_INPUT_MISSING` carries

`{ error, fields }` (no `errorClass`). A defensive `INVALID_BODY`

(`{ error, errorClass: 'INPUT', requestId }`) exists for unexpected

body-read failures.

Security Schemes

PatchesSignedRequest

type apiKey

Scoped partner authentication + request integrity. Every authenticated

request carries four headers:

`Authorization: PATCHES-Partner <clientId>:<keyId>`

`X-PATCHES-Timestamp: <epoch milliseconds>`

`X-PATCHES-Nonce: <opaque nonce, [A-Za-z0-9_-]{20,128}>`

`X-PATCHES-Signature: <lowercase-hex HMAC-SHA256>`

The signature is HMAC-SHA256 over the 5-field canonical string:

`${METHOD}\n${path}\n${timestamp}\n${nonce}\n${bodyHash}`

where `METHOD` is uppercase, `path` is the FULL request pathname

INCLUDING the `/api/partner/v1` prefix (the query string is NOT

signed), `timestamp` and `nonce` are the EXACT header values, and

`bodyHash` is the lowercase-hex sha256 of the RAW request body bytes

(a bodyless request hashes the empty string, keeping the signature

bound to the method).

Verification is cumulative: signature verification is the first gate

only and never replaces — and is never replaced by — the per-operation

tenant scoping (organization ownership), entitlement, capability, and

device/subject binding checks. Credential states: ACTIVE and GRACE

validate; RETIRED and REVOKED fail closed; a GRACE credential expires

at its retirement instant.
