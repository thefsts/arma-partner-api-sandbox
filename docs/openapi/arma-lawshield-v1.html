Description

Wire contract for protocol `arma-lawshield.v1`.

Scope — exactly the implemented v1 surface:

* `POST /api/lawshield/arma` — the Law Shield inbound gateway (verifies the

ARMA-signed envelope end-to-end, then forwards to the durable processor

and returns a signed receipt on acceptance).

* `GET /api/lawshield/integration-readiness` — unauthenticated readiness probe.

* `POST /process` and `GET /status` — the durable processor's

service-to-service routes (Bearer auth). The gateway calls `POST /process`

after verification; ARMA reconciliation calls `GET /status`.

Two security models, both cumulative with the other checks:

* Partner-facing (gateway + readiness): HMAC-SHA256 request signing over

the 4-field canonical string with the five `x-arma-*` headers. Signature

verification NEVER replaces tenant (org/case mapping), entitlement

(record-type allow-list + disclosure policy), or human-authorization

checks — every layer is enforced.

* Service-to-service (processor): Bearer token + gateway-forwarded

verified-context headers + full defense-in-depth re-validation.

Behavioral invariants (all fail-closed):

* Every error body is `{ error, transferId, accepted: false }` (gateway) or

`{ accepted: false, error, ... }` (processor) — raw runtime messages are

never echoed; unknown codes surface as the generic `INTEGRATION_REJECTED`

(gateway) or `PROCESSOR_PERSISTENCE_FAILED` (processor).

* Nonce single-use (gateway replay guard + authoritative processor nonce

registry) with a 10-minute validity window; timestamps must be within

±5 minutes.

* Idempotency: same key + same content collapses to the SAME deterministic

receipt (no second disclosure); same key + different content is an

integrity conflict, quarantined, never accepted.

* Durable writes (nonce + idempotency + transfer + receipt + audit) commit

in ONE transaction — partial outcomes cannot exist.

* Success receipts are signed over the EXACT serialized receipt bytes

(verify raw, never re-serialize).

* AI actors can never authorize a transfer (blocked at the gateway AND at

the processor).

* Minimum-necessary disclosure policy is enforced processor-side on the

flat redacted payload; the gateway enforces signature/hash/injection

screens only.

Operations
  • POST /api/lawshield/arma — submitTransfer
  • GET /api/lawshield/integration-readiness — getIntegrationReadiness
  • POST /process — processTransfer

submitTransfer — Submit an ARMA→Law Shield disclosure transfer. Inbound Transfer Gateway

The single inbound route for `arma-lawshield.v1` transfers.

Cumulative security controls, in enforcement order (all must pass — none

replaces any other):

1. Method — POST only (else 405 `METHOD_NOT_ALLOWED` with `Allow: POST`).

2. Content type — must start with `application/json` (else 415 `CONTENT_TYPE_NOT_ALLOWED`).

3. Kill switch — `LAW_SHIELD_ARMA_INTEGRATION_DISABLED` (else 503 `INTEGRATION_DISABLED`).

4. Signing secret configured (else 503 `INTEGRATION_NOT_CONFIGURED`).

5. Body size ≤ 1,048,576 bytes (else 413 `PAYLOAD_TOO_LARGE`).

6. All five `x-arma-*` headers present (else 401 `MISSING_SECURITY_HEADERS`).

7. Schema version — header must equal `arma-lawshield.v1` (else 422 `SCHEMA_VERSION_UNSUPPORTED`).

8. Nonce format — `[A-Za-z0-9_-]{20,128}` (else 400 `INVALID_NONCE`).

9. Timestamp freshness — ±5 minutes of server time (else 409 `STALE_OR_FUTURE_REQUEST`).

10. Body hash — `x-arma-content-sha256` must equal sha256 of the raw request bytes (else 401 `BODY_HASH_MISMATCH`).

11. HMAC signature over the 4-field canonical string (else 401 `INVALID_SIGNATURE`).

12. Body parses as JSON (else 400 `INVALID_JSON`).

13. Envelope validation — required fields, system route, record type,

human-only authorization, org/case mapping, timestamps/expiry,

payload hash, injection screening (codes below).

14. First-layer nonce replay guard (else 409 `REPLAYED_NONCE`).

15. Processor configured (else 503 `INTEGRATION_PROCESSOR_NOT_CONFIGURED`);

transport failures are structured 502s; processor outcomes are

reconciled and receipt-verified before a 200 is returned.

Order-of-evaluation notes (verified from the implementation):

* `transferId` is `null` in error bodies for all failures before the

envelope's `transferId` is read (steps 1–11); it carries the real

transfer id from step 12 onward.

* `REPLAYED_NONCE` (gateway layer) is thrown AFTER verification, so its

error body carries the real `transferId`.

* Every error body carries `accepted: false`. Error bodies never carry

`status: "ACCEPTED"`.

On success (200) the response body IS the receipt (15 fields) and is

signed over its exact serialized bytes — see the `X-LawShield-*` response

headers.

processTransfer — Process a gateway-forwarded transfer (service-to-service). Durable Processor

The durable processor's inbound route. The gateway calls this after it has

verified the ARMA request end-to-end; the forwarded headers carry the

gateway-verified context (`x-verified-arma-nonce`, `x-verified-arma-content-sha256`,

`x-integration-schema-version`, `x-integration-transfer-id`) over the

ORIGINAL raw envelope bytes under the Bearer token.

The processor never trusts the gateway blindly — it re-validates everything

defense-in-depth (Bearer auth, kill switch, forwarded-header consistency,

canonical envelope re-validation, payload-hash recompute, human-authorization

denial, org/case mapping, minimum-necessary disclosure policy) and then

commits nonce + idempotency + transfer + receipt + audit inside ONE

transaction.

Outcome model (all deterministic, gateway-compatible):

* 200 `accepted: true` — receipt fields (first delivery).

* 200 same receipt — duplicate delivery (fresh nonce, same idempotency

key + content): the stored deterministic receipt; no second disclosure.

* 200 `accepted: false` — business rejection (the processor's error code

+ transferId + idempotencyKey; `quarantined: true` +

`violationPaths` for the policy/integrity quarantine codes).

* 500 — persistence failure (everything rolled back; fail closed).

* 503 — kill switch active, or processor fault.

Business rejection codes: `ORG_MAPPING_MISSING`, `ORG_MAPPING_INACTIVE`,

`ORG_MAPPING_MISMATCH`, `CASE_MAPPING_MISSING`, `CASE_MAPPING_INACTIVE`,

`CASE_MAPPING_MISMATCH`, `AUTHORIZER_UNKNOWN`, `AUTHORIZER_INACTIVE`,

`AUTHORIZER_ORG_MISMATCH`, `AI_CANNOT_AUTHORIZE_TRANSFER`,

`RECORD_TYPE_NOT_ALLOWED`, `MINIMUM_NECESSARY_VIOLATION`,

`ALWAYS_REDACTED_FIELD_PRESENT`, `REPLAYED_NONCE`,

`IDEMPOTENCY_KEY_CONFLICT`, `STALE_OR_FUTURE_REQUEST`, plus the

envelope re-validation codes (`INVALID_FIELD_*`, `INVALID_JSON`,

`INVALID_TIMESTAMPS`, `INVALID_TIME_ORDER`, `INVALID_NONCE`,

`INVALID_SYSTEM_ROUTE`, `MAPPING_REQUIRED`, `ORG_MAPPING_MISMATCH`,

`CASE_MAPPING_REQUIRED`, `PAYLOAD_REQUIRED`, `PAYLOAD_HASH_MISMATCH`,

`PAYLOAD_STRUCTURE_TOO_DEEP`, `TRANSFER_EXPIRED`,

`AI_OR_EXECUTABLE_INSTRUCTION_BLOCKED`, `SCHEMA_VERSION_UNSUPPORTED`,

`RECORD_TYPE_NOT_ALLOWED`). A defensive fallback code `INVALID_ENVELOPE`

exists for a non-Error throw out of envelope re-validation (unreachable

in practice; every re-validation failure carries its structured code).

ProcessorBearer
getTransferStatus — Query durable transfer status for reconciliation (service-to-service). Durable Processor

Reconciliation inquiry over the ACTUAL durable upstream state — used by

ARMA after an ambiguous outcome (timeout, receipt mismatch, lost response)

instead of guessing. Lookup by `transferId` and/or `idempotencyKey`.

Quarantined state is exposed for human review.

The kill switch is checked FIRST — nothing (not even status) is served

while the processor is disabled.

Security Schemes

ArmaSignedRequest

type apiKey

HMAC-SHA256 request-signing scheme over the five required `x-arma-*`

headers. The signature is computed over the 4-field canonical string:

`schemaVersion + "\n" + timestamp + "\n" + nonce + "\n" + bodyHash`

where `bodyHash` is the lowercase-hex sha256 of the RAW request body

bytes, `timestamp` and `nonce` are the EXACT header values, and

`schemaVersion` is `arma-lawshield.v1`. Both the `x-arma-content-sha256`

header and the canonical `bodyHash` term are sha256-hex of the same raw

bytes. A bodyless request has no representation in this protocol (the

single route is a POST with a required body).

header x-arma-signature

ProcessorBearer

type http

Service-to-service Bearer token for the durable processor routes. The

gateway presents it when forwarding to `POST /process`; ARMA

reconciliation presents it for `GET /status`. Missing or invalid token

fails closed with `PROCESSOR_AUTH_FAILED`.

Bearer authentication is ADDITIVE to — never a replacement for — the

forwarded-context re-validation, canonical envelope re-validation, and

business-policy enforcement the processor performs on every request.

scheme bearer
